# Итоговое задание: фильтр спама

Ражнов Андрей, группа МКБ251.
Дисциплина «Применение ML в кибербезопасности».

## Задача

Нужно было пройти весь цикл: собрать письма, обучить модель, которая отличает
спам от обычной почты, упаковать её в сервис и выложить в интернет.
Дополнительно я сделал вторую модель — она определяет, о чём письмо: реклама,
предложение работы, знакомства, финансы, доставка, безопасность или другое.

Главное требование к качеству — поменьше ложных срабатываний. Если фильтр
выбросит нормальное письмо со счётом или ответом преподавателя, это хуже,
чем пропущенная реклама.

## Данные

Взял три источника:

| Источник | Что даёт | Сколько писем |
|---|---|---|
| SpamAssassin | обычная почта и спам, включая «трудные» нормальные письма | 6 155 |
| Ling-Spam | рассылка на другую тему, проверка переносимости | 2 875 |
| SpamBase (UCI) | 57 числовых признаков, по ним я считаю такие же признаки у своих писем | 4 601 |
| Мои примеры | 25 писем от сервисов: сброс пароля, квитанции, коды | 25 |

Итого 9 055 писем. Письма разбирал через MIME: из HTML доставал текст, кодировки
чистил. Удалил дубликаты — в двух архивах SpamAssassin одни и те же письма лежат
дважды. Отдельно проверил пересечение с тестовым набором: 1 203 письма из 1 545
оказались точными копиями писем из SpamAssassin, поэтому все совпадения убрал из
обучения.

После чистки осталось 7 848 писем: 6 278 для обучения, 1 570 для валидации и
1 545 — тест из задания. Списки и хеши разбиения лежат в
`artifacts/hackathon_v2/split_manifest.csv`, повторов между частями нет.

## Модель

Письмо превращается в три набора признаков:

1. TF-IDF по словам (1–2-граммы) и по символьным n-граммам (3–4) — символы нужны,
   чтобы ловить обфускацию вроде «в*и*а*г*р*а».
2. 94 числовых признака письма: длина, доля заглавных, число ссылок, служебные
   слова, признаки отправителя.
3. 50 признаков ссылок: для каждой ссылки считаются 24 свойства (IP вместо домена,
   имя пользователя в адресе, кодирование, похожесть на бренд, слова-приманки),
   потом берутся максимумы, средние и число ссылок.

Дальше работают четыре модели — логистическая регрессия, линейный SVM, Complement
NB и градиентный бустинг. Их вероятности складывает мета-модель (логистическая
регрессия). Мета-модель учится на OOF-предсказаниях: каждая строка предсказана
моделью, которая её не видела, поэтому утечки из обучения в мета-слой нет.

Порог решил по валидации: максимум полноты при доле ложных срабатываний не выше
1 %. Получилось значение 0.710376. Тестовые метки при выборе порога не
использовались.

## Результаты

| Выборка | Писем | F1 | Precision | Recall | Ложные срабатывания |
|---|---:|---:|---:|---:|---:|
| Валидация (по ней выбран порог) | 1 570 | 0.98204 | 0.97910 | 0.98498 | 7 из 1 237 |
| Тест из задания | 1 545 | 0.93878 | 0.99184 | 0.89110 | 7 из 590 |
| Отдельный срез | 342 | 0.84342 | 0.97131 | 0.74528 | 7 из 24 |

На тесте из задания доля ложных срабатываний 1.19 %. Все 1 545 тестовых писем
исключены из обучения и валидации.

Срез из 342 писем — то, что осталось после удаления совпадений. Нормальных писем
там всего 24, поэтому 7 ошибок дают сразу 29 % ложных срабатываний. Это честная
оценка на незнакомой почте, и она показывает главную слабость: сервисные
уведомления похожи на фишинг.

Модель категорий даёт macro-F1 0.72248. Разметка категорий сделана правилами по
словам, поэтому метрика показывает, насколько модель повторяет эти правила, а не
совпадение с мнением человека.

## Ограничения

* Русских писем в обучении почти нет: корпуса англоязычные. На русском тексте
  модель ошибается чаще.
* Транзакционные письма (сброс пароля, подтверждение адреса, квитанции) похожи на
  фишинг по словам. Это основной источник ложных срабатываний.
* Близкие дубликаты и цепочки переписки я не группировал. Для честной проверки
  нужен свежий набор писем, собранный позже.
* Сервис возвращает вероятность и категорию. Финальное решение лучше оставлять
  человеку, особенно для писем у порога.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r service/requirements.txt
.venv/bin/python scripts/fetch_models.py artifacts   # скачает модели, 38 и 12 МБ
.venv/bin/uvicorn service.app:app --host 127.0.0.1 --port 8000
```

Форма откроется на `http://127.0.0.1:8000`, документация API — на `/docs`.
Проверка одного письма:

```bash
curl -s -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{"text": "Congratulations! You won $1,000,000. Click here to claim your prize!"}'
```

В Docker:

```bash
docker build -t mkb251-razhnovap-antispam .
docker run --rm -p 8000:8000 mkb251-razhnovap-antispam
```

Или `docker compose up --build`. Конфигурация для Render лежит в `render.yaml`.

## Воспроизведение с нуля

```bash
bash scripts/download_data.sh      # корпуса и тест из задания
bash run.sh                        # данные, обучение, категории, метрики
```

## Что где лежит

* `src/` — разбор писем, признаки, обучение, адаптер признаков ссылок.
* `service/` — FastAPI, форма и Dockerfile.
* `scripts/` — загрузка данных и моделей.
* `artifacts/` — метрики, манифест моделей, список разбиения.
* `reports/` — выполненная тетрадка и отчёт.

Модели хранятся не в репозитории, а в разделе Releases: они весят 38 и 12 МБ.
`scripts/fetch_models.py` скачивает их и сверяет контрольные суммы по
`artifacts/model_manifest.json`.

Признаки ссылок взяты из моей прошлой работы по фишинговым адресам
(https://github.com/Andrey123654/Hakaton): код лежит в `src/vendor/`, ссылка на
исходный коммит указана в `src/vendor/README.md`. Веса той модели и её метрики
сюда не переносились, эта модель обучена заново на письмах.
